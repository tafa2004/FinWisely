# FinWisely Database Design

## 1. Overview

FinWisely is a small digital banking transaction management prototype developed to demonstrate database security and transaction integrity using MySQL and Java. It uses fictional demonstration records only. It is not connected to a real bank and does not process real money.

The database is named `finwisely` and uses MySQL with the InnoDB storage engine. The Java console application connects through JDBC and uses a restricted database service account.

## 2. Database components

The database contains five principal tables:

| Table | Purpose |
|---|---|
| `customers` | Stores fictional customer details used by the prototype. |
| `accounts` | Stores customer account details, account type, status and current balance. |
| `transactions` | Stores deposit and withdrawal records associated with accounts. |
| `audit_logs` | Stores audit entries generated by the transaction-insert trigger. |
| `app_users` | Stores application login usernames, password hashes and application roles. |

## 3. Relationships

- One customer can have multiple accounts. `accounts.customer_id` references `customers.customer_id`.
- One account can have multiple transactions. `transactions.account_id` references `accounts.account_id`.
- The transaction audit trigger creates an audit-log record when a transaction is inserted.

The foreign-key relationships help prevent transactions from referring to accounts that do not exist and accounts from referring to customers that do not exist.

## 4. Keys, constraints and indexes

The schema uses primary keys to identify records and foreign keys to enforce relationships. Unique constraints are applied to selected customer identifiers, including email and national ID.

Important integrity rules include:

- Account balances must not be negative.
- Account types are restricted to the supported values, `Savings` and `Current`.
- Account statuses are restricted to `ACTIVE`, `FROZEN` and `CLOSED`.
- Transaction types are restricted to `DEPOSIT` and `WITHDRAWAL`.
- Transaction amounts must be greater than zero.

Indexes are provided for commonly queried or joined fields to support database operations.

## 5. Transaction audit trigger

The `trg_transactions_insert` trigger runs after a row is inserted into `transactions`. It creates a corresponding row in `audit_logs`, recording information such as the acting username, action, table name, record ID, account ID, transaction type, amount and timestamp.

The trigger operates as part of the database transaction. If the transaction that caused the trigger to run is rolled back, the corresponding audit-log insertion is also rolled back.

**Scope limitation:** the implemented trigger audits transaction inserts. It should not be described as auditing every update or delete across the database.

## 6. Database users and permissions

The project demonstrates role-based access control using separate MySQL roles and accounts:

- **Administrator:** broad administrative privileges on the project database.
- **Teller:** permissions required for the demonstrated teller operations, including reading customer/account information, updating account balances, and reading/inserting transactions.
- **Auditor:** read-only access for reviewing database records.
- **Application service account (`app_service`):** restricted privileges used by the Java application. It can read the required customer/account and application-user data, update account balances, and read/insert transactions. It is not granted access to audit logs or permission to update account status.

The exact effective permissions are defined in the SQL setup scripts.

## 7. Setup scripts

The `database` directory contains numbered SQL scripts:

1. `01_create_tables.sql` — creates the database objects and transaction audit trigger.
2. `02_sample_data.sql` — inserts fictional demonstration data.
3. `03_users_permissions.sql` — creates database roles/users and grants permissions.
4. `04_security_tests.sql` — contains SQL statements for demonstrating permitted and denied operations.
5. `05_app_users.sql` — sets up application users and the restricted application service account.

Run setup scripts in the documented order using an appropriately privileged MySQL account. The security-test script includes statements expected to be denied; execute those demonstrations individually where necessary so that one expected error does not prevent later tests from running.

## 8. Design considerations and limitations

The design demonstrates relational integrity, least-privilege permissions, transaction records and trigger-based audit logging. It is an academic prototype with fictional data. It is not a production banking database and does not implement a full banking core, real customer onboarding, regulatory reporting, high availability, or a complete operational security programme.
